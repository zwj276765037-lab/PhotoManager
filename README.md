# PhotoManager（AI 朋友圈拼图）

基于微信小程序的 AI 朋友圈照片拼图项目。

当前阶段：产品方向已从“大量照片管理分类”调整为“AI 自动生成朋友圈风格拼图”。`goal/README.md` 已进入 v0.3 待审核稿，业务代码将在本轮需求审核通过后进入 `workspace/`。

## 目录约定

```text
PhotoManager/
├── goal/       # 项目需求、功能范围、验收标准、上线说明
├── mission/    # 每一次优化的时间、内容、验证结果和提交记录
└── workspace/  # 微信小程序、云函数/后端和测试代码
```

三个目录的职责不能混用：

- `goal/` 回答“要做什么、做到什么程度”。
- `mission/` 回答“何时做了什么、是否验证通过”。
- `workspace/` 存放“实际运行的代码”。

## 最底层工作方式

用户主动选择 2～9 张照片，小程序负责选图、低清预览和轻量编辑；云端负责 AI 分析、受控背景生成、高清渲染、内容安全与必要的 AI 标识。第一版采用以下数据流：

```text
用户选择 2～9 张照片
        ↓
私有上传与输入内容安全检查
        ↓
AI 分析主体、色彩、方向和构图
        ↓
生成 3 个低清拼图候选
        ↓
用户调整风格、布局、裁切焦点和文字
        ↓
服务端高清渲染与输出复检
        ↓
保存到相册或打开微信原生图片分享面板
```

底层数据分为三部分：

1. 私有临时文件：用户原图、中间稿和预览图，按明确期限自动清理。
2. 设计参数：照片顺序、裁切焦点、风格、布局、文字和颜色，可用于恢复任务和重新渲染。
3. 输出文件：服务端生成的高清拼图，通过短期地址下载后保存或分享。

MVP 优先采用微信小程序前端、私有对象存储、异步任务服务和服务端渲染。AI 密钥只保存在服务端，生成服务不可用时仍可降级为普通模板拼图。

## 每次成果的交付规则

每一轮修改都按以下顺序完成：

1. 在 `goal/` 确认或更新需求与验收标准。
2. 只在 `workspace/` 修改项目实现。
3. 完成与变更风险相匹配的检查或测试。
4. 在 `mission/` 追加日期、优化内容、验证结果和未解决问题。
5. 提交 Git，并推送到 `origin/main`：<https://github.com/zwj276765037-lab/PhotoManager>。

这里的“覆盖到 GitHub”定义为：GitHub 的 `main` 分支是最终成果基线，每次成果都提交并正常推送。默认不使用强制推送，以免误删远端历史；只有明确要求重写历史且确认备份后才会执行。
