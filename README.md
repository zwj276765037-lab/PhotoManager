# PhotoManager

基于微信小程序的照片管理与分类项目。

当前阶段：项目初始化。此版本先确定需求、研发记录、代码之间的边界，以及照片管理功能的最底层工作方式；业务代码将在需求确认后进入 `workspace/`。

## 目录约定

```text
PhotoManager/
├── goal/       # 项目需求、功能范围、验收标准、上线说明
├── mission/    # 每一次优化的时间、内容、验证结果和提交记录
└── workspace/  # 微信小程序、云函数/后端和测试代码
```

三个目录的职责不能混用：

- `goal/` 回答“要做什么、做到什么程度”。
- `mission/` 回答“何时做了什么、是否验证通过”。
- `workspace/` 存放“实际运行的代码”。

## 最底层工作方式

照片管理不是让小程序静默扫描手机相册。受微信权限与隐私机制限制，照片必须由用户主动选择或拍摄后导入。第一版采用以下数据流：

```text
用户选择/拍摄照片
        ↓
小程序读取可用的基础信息（临时文件、尺寸、大小、导入时间）
        ↓
原图上传到云存储，数据库保存照片索引
        ↓
规则分类（日期、类型、用户相册、标签）
        ↓
可选的云端 AI 分类（场景、物体、OCR；人脸功能另行评估合规性）
        ↓
按相册/标签/日期检索、预览、修改分类和删除
```

底层数据分为两部分：

1. 文件存储：保存原图和缩略图，数据库不直接保存图片二进制。
2. 索引数据：每张照片对应一条记录，至少包含所有者、文件地址、缩略图、导入时间、拍摄时间（能够获得时）、宽高、大小、标签、相册和状态。

MVP（首个可用版本）优先使用微信云开发，减少自建服务器、域名和鉴权工作。后续如果 AI 计算量或跨平台需求增加，再把分类服务拆成独立后端。

## 每次成果的交付规则

每一轮修改都按以下顺序完成：

1. 在 `goal/` 确认或更新需求与验收标准。
2. 只在 `workspace/` 修改项目实现。
3. 完成与变更风险相匹配的检查或测试。
4. 在 `mission/` 追加日期、优化内容、验证结果和未解决问题。
5. 提交 Git，并推送到 `origin/main`：<https://github.com/zwj276765037-lab/PhotoManager>。

这里的“覆盖到 GitHub”定义为：GitHub 的 `main` 分支是最终成果基线，每次成果都提交并正常推送。默认不使用强制推送，以免误删远端历史；只有明确要求重写历史且确认备份后才会执行。
